### 失败用例 1：test_screener_data_quality —— 测试脆弱 + 数据源降级不彻底（非代码回归）

- **全量跑失败原因**：`run_screener()` 返回 `None`。日志实证：baostock 数百次 `you don't login.`（登录失败无退避）、akshare 3 次 `Connection aborted`、腾讯行情融合 0/213 只 → "数据不足，无法运行选股" → 断言 `screener_result` 失败。
- **单独跑结果**：210 秒后 **skip**（无推荐标的），非失败。说明失败与全量套件中的网络资源竞争/限流有关，**测试顺序依赖、网络脆弱**。
- **暴露的真实问题**（非测试问题）：
  1. 全部数据源失败时 `run_screener()` 返回 None，**无缓存兜底、无陈旧数据标识**（见 P1-16）；
  2. baostock `_bs_login` 失败后每次请求都重新登录，**无退避/熔断/线程安全**（见 P1-14）。
- **修复建议**：测试对 `@pytest.mark.network` 用例在数据源全挂时应 skip 而非 fail（pytest.ini 注册 network mark + conftest 网络探测）；`run_screener` 增加"数据源全挂→明确报错/降级用缓存并标识 stale"。

### 失败用例 2：test_ratchet_stop_loss —— 测试断言过时 + 持仓数据异常（双重原因）

- **断言与系统设计矛盾（测试过时）**：测试断言所有持仓 `stop_loss < buy_price`。但移动止损权威源 `compute_trailing_stop`（`strategy/trend_strategy.py:735-769`）明确规定：浮盈 3%-15% 时止损上移到 **buy×1.01（保本+1%）**，浮盈 >15% 时到 buy×1.12/1.22 —— **止损价高于买入价是 Ratchet 锁盈的设计行为**。当前 600887（stop 26.44 = buy 26.175×1.01）、600256（stop 6.63 = buy 6.562×1.01）均属合法保本档，测试误报违规。
- **数据异常（真实问题）**：
  - **600989**：buy=42.527、current=22.46（浮亏 -47%）、**stop_loss=25.33 > 现价 22.46**。止损价高于现价意味着盘中监控每轮都应触发止损确认；且 25.33 不符合任何 Ratchet 档位（初始止损应为 42.527×0.9=38.27）。疑似除权/拆股或手工修正后 stop_loss 未同步重算。**需人工核实该持仓**。
  - 排查期间发现根目录 holdings.json 刚被更新：562590 由（buy=0.449, shares=20800, stop=0.845——止损高出成本 88% 的违规现场）修正为（buy=0.853, shares=134900, stop=0.845）。印证"成本修正后 stop_loss 不重算、Ratchet 只升不降卡死高位"的风险模式真实存在过（见 P1-08）。
- **修复建议**：测试断言改为 `stop_loss ≤ buy_price×1.22`（Ratchet 最高档）且 `stop_loss` 与 `compute_trailing_stop(buy_price, current_price)` 或历史最高价档位一致；同时增加 `stop_loss > current_price` 的"止损已穿透仍持仓"数据一致性告警。

## 二、P0 问题（影响资金安全）

### P0-01 ✅复核 | V2.0 sys.path 清理回归：main.py 无法启动，scheduler 邮件任务静默失败
- **现象**：`python trading_system/main.py` → `ModuleNotFoundError: No module named 'output.condition_sheet'`（main.py:46）。根级 `output/` 包位于仓库根，而 `trading_system/__init__.py` 的统一注入只覆盖包目录本身、且脚本模式根本不执行包 `__init__.py`。scheduler.py:1336/1495/1519 的 `output.eastmoney_orders`（盘后条件单邮件）、`output.morning_brief`（晨间简报）为 try 块内惰性导入 → **运行时静默失败，条件单邮件漏发等同交易指令丢失**。
- **位置**：`trading_system/main.py:32-34,46`；`trading_system/scheduler.py:1336,1495,1519`；`trading_system/__init__.py:37-44`
- **复现**：`python trading_system/main.py --help`
- **修复**：入口脚本（main.py/scheduler.py）顶部恢复对**仓库根目录**的 sys.path 注入；或统一 `python -m trading_system.main` 运行方式；惰性 `output.*` 导入失败必须显式告警而非 `pass`。

### P0-02 ✅复核 | `_do_check_buy` holdings 键名契约不匹配 → 6 道仓位硬约束集体静默失效
- **现象**：`risk_control.py` `_do_check_buy` 各关卡读 `pos.get("cost")/pos.get("price")`（L1616-1617/1641/1662/1674-1676/1693/2048），而生产调用方（`intraday_decision.py:102-115` `load_holdings()` ✅复核原样返回 holdings.json 结构、`alert_engine.py:933`）传入的键是 `buy_price/current_price` → 市值恒为 0 → **浮亏加仓拦截、单票 15%/20%、赛道 40%、总仓位、现金安全垫、组合浮亏 -10% 六道关卡全部形同虚设**。同文件 `_calc_current_total_assets:1901-1902` 有正确的 4 级 fallback，证明是疏漏而非设计。
- **影响**：盘中加仓决策与 R18 加仓提醒唯二两条 `check_buy` 生产路径。当前靠 `pause_until=2026-10-12`（连亏熔断）偶然兜底，暂停期结束后所有仓位约束裸奔。
- **修复**：`quick_risk_check`（risk_control.py:658-671）入口统一归一化 holdings 键名（`buy_price→cost`、`current_price→price`、`stock_type→type`）；补一个喂真实 holdings.json 结构的断言测试。

### P0-03 ✅复核 | 大盘暴跌（≤-2.5%）时整个个股止损流水线被跳过，且系统性风险告警不可达
- **现象**：`intraday_monitor.py:506-509` `gate_state == "suppress"` 直接 `return alerts` —— 后续个股硬止损确认、梯度减仓、急跌、止盈全部停摆，止损缓冲计时冻结；而 L517 的系统性风险硬止损告警条件是 `gate_state in ("delay","suppress")`，**suppress 分支永远到不了**（逻辑倒挂：跌 -1%~-2.5% 会告警，跌得更狠反而不告警）。
- **影响**：系统性风险最高、最需要止损的时刻，盘中监控形同关闭。
- **修复**：suppress 仅压制 info 级噪音，critical/emergency 止损与减仓必须穿透门控（与 L1231 已有"风控信号穿透"原则一致）；系统性风险告警移到早返回之前。

### P0-04 ✅复核 | qmt_trader 条件单状态零持久化：进程重启即重复下单
- **现象**：`ConditionOrder.__init__`（qmt_trader.py:94-95）硬编码 `triggered=False, executed=False`，忽略 JSON 中已有状态；全文**零文件写入**；`executed_today`（auto_scheduler.py:150）纯内存；无单实例 PID 锁（对照 scheduler 有 `.scheduler.pid`+心跳双保护）。

- **修复**：状态字段落盘（atomic_json_write）+ `__init__` 读取而非重置；启动写 `.qmt_trader.pid` 单实例锁；下单前查 `query_stock_orders` 在途委托去重。

### P0-05 ✅复核 | 拿到 order_id 即视为"已执行"，拒单回调无人消费 → 止损单被废后静默漏单
