## 二、业务 bug 与风险隐患清单

### 2.1 P0 级（影响交易决策/回测可信度/风控有效性）

#### P0-A：报告成本口径声明与实际不一致

- **现象**：`master_report.py` 附录声明"佣金万2.5、印花税千1"，但 config.py 实际为"佣金万3、印花税万5"
- **位置**：`trading_system/backtest/master_report.py` L568
- **影响**：回测报告的成本口径声明不可信，审计人员会被误导
- **验证**：对比 config.COMMISSION_RATE × 10000 vs 报告声明
- **修复**：报告附录的成本口径从 config 动态读取，不硬编码
- **验收**：报告声明的佣金/印花税率 == config 实际值

#### P0-B：config.py 成本参数三处定义，修改易遗漏

- **现象**：`COMMISSION_RATE`/`STAMP_TAX_RATE` 在 config.py 顶层定义一次（L1067-1070），但在 `BACKTEST_SAMPLE`（L1601-1602）和 `MASTER_BACKTEST_CONFIG`（L1874-1876）又各定义一次
- **影响**：修改费率时需同步三处，否则回测/报告/成本敏感性使用不同费率
- **修复**：`BACKTEST_SAMPLE` 和 `MASTER_BACKTEST_CONFIG` 中的成本参数改为引用全局 `COMMISSION_RATE`/`STAMP_TAX_RATE`，消除重复定义
- **验收**：`grep -n "0.0003\|0.0005" config.py` 仅剩全局定义处

#### P0-C：核心模块零测试覆盖

- **现象**：以下核心模块无任何单元测试：
  - `data/data_loader.py`（数据加载，含复权/停牌/退市处理）
  - `risk/risk_control.py`（风控引擎，仓位/熔断/止损）
  - `strategy/stock_screener.py`（选股引擎）
  - `scheduler.py`（调度器，3721 行）
- **影响**：这些模块的 bug 只能在实盘/回测中暴露，无法在 CI 拦截
- **修复**：按风险排序补测试：risk_control > data_loader > stock_screener > scheduler
- **验收**：每个模块至少覆盖核心路径（风控硬约束、数据加载过滤、选股信号生成）

#### P0-D：`sys.path.insert` 反模式遍布 25+ 文件

- **现象**：25+ 个 .py 文件使用 `sys.path.insert(0, ...)` 手动修改模块搜索路径
- **影响**：
  - 模块导入顺序依赖运行时的 cwd，不同入口可能加载不同版本
  - 隐藏了真实的包结构依赖，增加调试难度
  - 与 `setup.py`/`pip install -e .` 的标准 Python 包管理冲突
- **修复**：
  1. 确保 `setup.py` 正确声明包结构（`packages=find_packages()`）
  2. 开发环境用 `pip install -e .` 安装
  3. 逐文件移除 `sys.path.insert`（保留 scripts/ 下的独立脚本，因其需自举）
- **验收**：`grep -r "sys.path.insert" trading_system/` 返回 0 条

### 2.2 P1 级（影响效率/质量/稳定性）

#### P1-A：config.py 单文件 2029 行，职责过多

- **现象**：config.py 包含：股票池、因子权重、回测参数、风控阈值、调度配置、报告模板、成本参数、WF 配置、门限等
- **影响**：修改一个配置需在大文件中定位，易冲突；不同职责的配置耦合
- **修复**：按职责拆分为 `config/` 子包：`config/pool.py`、`config/backtest.py`、`config/risk.py`、`config/report.py`、`config/__init__.py` 聚合导出
- **验收**：`from config import COMMISSION_RATE` 等现有导入路径不变

#### P1-B：scheduler.py 单文件 3721 行

- **现象**：调度器包含：时间轮询、任务分发、条件单执行、报告生成、异常恢复、日志管理等
- **影响**：单文件过大，难以测试和维护
- **修复**：拆分为 `scheduler/` 子包：`task_runner.py`、`alert_executor.py`、`report_scheduler.py`、`watchdog.py`
- **验收**：`python auto_scheduler.py` 行为不变

#### P1-C：data/*.json 状态文件无轮转/清理机制

- **现象**：`margin_monitor_cache` 每日备份但无自动清理；`prediction_history.json`（161KB/500条）、`slippage_history.json`（104KB/275条）无限增长
- **影响**：磁盘占用持续膨胀（已 720MB+），加载变慢
- **修复**：
  1. 备份文件添加保留天数上限（如 7 天）
  2. history 类文件添加最大条目数限制（如 1000 条，FIFO 淘汰）
- **验收**：连续运行 30 天后，data/ 目录大小稳定不增长

#### P1-D：回测引擎间成本参数传递不统一

- **现象**：
  - `backtest_optimizer.py` 使用模块级常量 `SLIPPAGE_LEADER`/`SLIPPAGE_FLEX`
  - `backtest/broker.py` 从 config 读取
  - `cost_sensitivity.py` 通过 monkeypatch 修改常量
- **影响**：monkeypatch 方式脆弱，并行测试会互相干扰
- **修复**：统一通过 `CostConfig` 数据类传递，不依赖全局常量
- **验收**：`cost_sensitivity.py` 的四档测试结果与 monkeypatch 前一致

### 2.3 P2 级（架构优化/长期演进）

#### P2-A：回测入口分散（7 个独立文件）

- **现象**：`trading_system/` 根目录有 7 个 `run_*backtest*.py` / `backtest_*.py`
- **影响**：新用户不知道用哪个；维护时可能漏改
- **修复**：统一到 `scripts/master_backtest.py`，旧入口添加 `@deprecated` 注释并指向 master
- **验收**：旧入口仍可运行但打印 deprecation warning

#### P2-B：测试文件命名不规范

- **现象**：20 个测试文件，部分以 `test_deep_*`、`test_safety_*` 等模糊命名
- **影响**：难以快速定位测试覆盖的模块
- **修复**：按被测模块命名：`test_data_loader.py`、`test_risk_control.py`、`test_stock_screener.py`

#### P2-C：缺少类型注解与 dataclass

- **现象**：大量函数无类型注解，配置用裸 dict 传递
- **影响**：IDE 补全差、运行时类型错误难发现
- **修复**：逐步添加 `typing` 注解，核心配置用 `dataclass` 或 `NamedTuple`
- **验收**：`mypy trading_system/backtest/metrics.py` 无错误（先从一个模块试点）
